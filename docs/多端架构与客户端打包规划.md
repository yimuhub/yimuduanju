# 多端产品形态与部署架构规划

> 一幕·YIMU AI 短剧工坊 · 多端化与客户端打包总体设计
> 版本：v1.0（2026-10-29）
> 依据：`README.md`、`docs/功能列表.md`、`docs/企业版部署.md`、`server/app.module.ts`、`scripts/start.sh`、`scripts/gateway.js` 现状盘点
> 定调（已确认，本文只做细化不改方向）：**最终形态以客户端为主，网页版作为存在形式之一；后台统一，一套代码两种部署。**

## 一、现状盘点（改造的起点）

| 现状 | 依据 | 对多端化的影响 |
|---|---|---|
| 后端 NestJS 10 + Drizzle，19 个业务模块（项目/分镜/生成/资产/导出/计费/质检…） | `server/app.module.ts` | 核心域完整，可原样复用为统一后台 |
| 本地启动依赖 Homebrew PostgreSQL 16 + 可选 Redis，Node ≥ 22 | `scripts/start.sh`（L50-150） | **桌面打包最大障碍**：PG/Redis 不能要求用户 brew 安装 |
| 本地网关 Node 进程：伺服 `dist/client` + 转发 API + **注入单用户身份头**，且已预留 `x-yimu-user-id` 多用户分支 | `scripts/gateway.js`（L7、L50、L161-175） | 用户体系已有一处"接缝"，云端多租户可从此处正式化 |
| 任务队列 BullMQ，Redis 不可用时**自动降级进程内串行** | `server/modules/generation/job-worker.service.ts`（L37-147） | 单机形态天然可去掉 Redis 依赖，云端形态启用队列并发 |
| 对象存储为直传签名桩（S3 环境变量存在则返回预签名，否则 local 模式） | `server/modules/storage/storage.service.ts` | 存储抽象已留桩，补真实驱动即可 |
| License 校验、管理令牌、审计拦截器（migration 0003）已存在 | `docs/企业版部署.md`、`server/modules/admin/`、`AuditInterceptor` | 商业授权底座已有，需升级为在线校验 |
| 成片 MP4 由**浏览器端 FFmpeg.wasm** 合成；导出模块引用服务端 ffmpeg | `client/src/utils/ffmpegSynth.ts`、`server/modules/export/export.service.ts` | 客户端形态应改为本地 ffmpeg 进程（更快更稳） |
| 无用户体系/无鉴权中间件（除管理令牌），计费模块为**项目成本核算**而非 SaaS 收费 | `server/modules/billing/billing.service.ts` | 云端 SaaS 的两大空白：鉴权、计费收单 |

结论：**统一后台已具雏形，缺的是"身份 + 租户 + 收单"三层商业能力，以及"本地依赖内嵌"的打包能力。**

## 三、桌面客户端技术选型：Tauri 2 vs Electron

### 3.1 对比

| 维度 | Tauri 2 | Electron |
|---|---|---|
| 安装包体积 | 8~15 MB（宿主用系统 WebView） | 90~120 MB（自带 Chromium+Node） |
| 常驻内存 | 低（无内置 Chromium） | 高 |
| Node 后端承载 | 需 **sidecar**：把 NestJS 编译产物打成独立 Node 可执行文件 | **主进程直接 require 后端**，最省事 |
| spawn ffmpeg | Rust `Command` 或 sidecar 均可 | 主进程 `child_process`，天然顺手 |
| 自动更新 | 官方 updater 插件（签名清单） | electron-updater（成熟） |
| 代码签名 | macOS 公证 / Windows EV 证书流程均有官方文档与 GitHub Action | 同样成熟 |
| 多窗口/托盘/协议 | 插件齐全 | 内置 |
| 团队成本 | 需要少量 Rust（仅壳层，业务不用写） | 全 JS，学习成本最低 |

### 3.2 明确推荐：Tauri 2（Rust 壳 + Node sidecar）

理由：

1. **后端是独立 HTTP 进程，不是库**。现有启动方式是 `npx nest start`（`scripts/start.sh` L174-198）——后端本来就是一个监听 3000 端口的独立进程，前端经网关 5173 访问。这与 Electron"主进程内嵌后端"的优势关系不大：Tauri 壳只负责拉起 sidecar + 加载 WebView，架构映射同样干净。
2. **体积与体验是客户端产品的硬指标**。产品要发给非技术创作者（见 `docs/操作说明书.md` 的目标用户），100 MB 级 Electron 包 + 高内存会让"轻量工具"定位打折；且本地还要内嵌 PostgreSQL（约 30~50 MB）与 ffmpeg（约 80 MB），Electron 的 100 MB 冗余更难接受。
3. sidecar 打包方案已成熟：Node 22 官方 SEA（Single Executable Application）或 Bun `bun build --compile`，把 `nest build` 产物（`main.js`）+ `node_modules` 打成单文件可执行程序，Tauri 以 `externalBin` 声明（tauri.conf.json），随应用签名分发。**已知风险**：`@lark-apaas/fullstack-nestjs-core`（`package.json` L46）若含动态 require 需在打包时逐个验证——这是选 Tauri 的唯一技术赌注，P0 第一周做 spike 验证，**若验证失败则整题切换 Electron**（备选预案明确，不作二次论证）。
4. 自动更新与签名：Tauri updater 支持更新清单签名；macOS 走 Developer ID + notarytool 公证，Windows 走 EV 代码签名证书（解决 SmartScreen 拦截），均有现成 GitHub Actions 模板。

### 3.3 本地 PostgreSQL 的处理（关键决策）

| 方案 | 改动量 | 体积 | 结论 |
|---|---|---|---|
| A. 内嵌 PostgreSQL 二进制（`embedded-postgres` npm 包，按平台携带 PG 16/17 二进制） | **零**：`scripts/db-init.sql`、`scripts/migrate.js`、全部 SQL 原样可用 | +35~50 MB | **P1 采用** |
| B. 换 SQLite（Drizzle 支持 SQLite 方言） | 大：`db-init.sql` 及增量迁移为 SQL-first，需维护 pg/sqlite 双方言；JSONB/数组类型要改 | +2 MB | P2 评估，仅当包体积成为增长瓶颈再做 |
| C. 要求用户自装 PG（现状） | 零 | 0 | 桌面版不可接受，废弃 |

选 A 的核心理由：本项目迁移是 **SQL-first**（`scripts/start.sh` L137-157：`db-init.sql` + `scripts/migrate.js` 逐条执行），换 SQLite 意味着全量重写迁移脚本与数据类型，风险与收益不成比例。embedded-postgres 由 Tauri sidecar 启停，数据目录放在 `~/Library/Application Support/yimu/`（macOS）等平台标准位置，`stop.sh` 逻辑收编进壳层生命周期管理。

Redis **不打包**：`job-worker.service.ts` 已实现无 Redis 降级（L119-147），本地形态直接走进程内串行/低并发模式，零改造。

### 3.4 ffmpeg 与 BSL 1.1 合规注意点

- ffmpeg：桌面版用 `ffmpeg-static` 按平台携带静态二进制，导出改为服务端合成（替代浏览器 FFmpeg.wasm 的 `client/src/utils/ffmpegSynth.ts` 路径），进度经 WebSocket 回传。注意 ffmpeg LGPL 构建需禁用 GPL 组件（x264 需 `--enable-gpl`，若必须用 x264 则遵守 GPL 动态调用隔离或改用开源友好编码器并在 NOTICE 声明）。
- **BSL 1.1（`LICENSE`、`package.json` L5）合规要点**：
  1. 我方是版权方（yimu.hyipf.com），可对自研代码任意分发，但**给用户的授权条款要重新表述**：客户端安装包属于"再分发/闭源商用"形态，需在 EULA 中明确授权范围，引用 LICENSE 的免费层/商业授权分层（连续 12 个月商业价值 < 10 万元免费，否则需商业授权）；
  2. BSL 1.1 的 Additional Use Grant 需要增补"允许安装与使用官方发行的分发版客户端"条款（当前 LICENSE 面向源码使用场景，未覆盖二进制分发），由律师复核后随 2.3 版本更新；
  3. 第三方依赖审计：打包容器内所有 npm 依赖 + 内嵌二进制（PG: PostgreSQL License；ffmpeg: LGPL/GPL；Tauri: MIT/Apache）做 license 清单，排除 GPL 传染风险进闭源包；
  4. 商标："一幕·YIMU"商标需另行授权（README L90），客户端与安装包上的品牌使用以自持商标注册为前提，尽快提交注册；
  5. 满四年自动转 Apache 2.0 的版本（README L89），其对应客户端版本转 Apache 后的再分发义务要在 EULA 版本化条款中说明。

### 3.5 桌面端打包流水线与产物结构

```
desktop/                        # 新增 Tauri 工程（P1）
├─ src-tauri/
│  ├─ tauri.conf.json           # externalBin 声明 sidecar 与 ffmpeg
│  ├─ capabilities/             # 最小权限（网络、文件系统仅限应用数据目录）
│  └─ binaries/                 # CI 产出：yimu-server-{platform}.exe、ffmpeg、pg/
├─ src/                         # 壳层 TS：窗口/托盘/更新/后端生命周期管理
└─ backend-bundle/              # nest build 产物（main.js + 精简 node_modules）
```

CI（GitHub Actions）矩阵：`macos-latest`（universal2 dmg + notarytool 公证）、`windows-latest`（NSIS/MSIX + EV 签名）、`ubuntu-latest`（AppImage + deb）。发布走 Tauri updater 清单（`latest.json` 签名），客户端启动时静默检查、用户确认更新。

### 3.6 客户端启动生命周期（本地模式）

```
Tauri 壳启动
 → 1. 唤起内嵌 PostgreSQL（embedded-postgres，数据目录 %APPDATA%/yimu/pg）
 → 2. 幂等执行 db-init.sql + scripts/migrate.js 逻辑（复用现有迁移器）
 → 3. 唤起 yimu-server sidecar（端口自动选 3000~3099，避免占用冲突，沿用 start.sh 的端口检测思路）
 → 4. 健康检查 GET / 通过后加载 WebView（保持 /app/yimu/ 路由 basename，与云端一致，README L75）
 → 5. 退出时反序关停（sidecar → PG），杜绝孤儿进程（替代现 stop.sh 的手工 pid 管理）
```

## 四、移动端与轻端选型

原则：**移动端不做全功能复刻**。画布（`@xyflow/react`）、时间线、导演台是重度桌面交互（`docs/功能列表.md` §8），移动端定位为"**盯进度 + 轻创作 + 分享传播**"。

| 端 | 选型 | 理由 |
|---|---|---|
| Android / iOS | **React Native + Expo** | 团队栈是 React 19 + TS（`client/`），RN 可复用 `shared/` 中的类型与 API client 代码、React Query 数据层；Expo 提供 EAS Build/Update（OTA 更新），免自建打包流水线。核心页面：项目列表/创建/任务进度/资产预览/灵感速记/成片播放分享 |
| 鸿蒙 NEXT | **两条腿**：① P1 用 ArkWeb 内核壳加载云端 H5（成本最低、先占位上架华为应用市场）；② P2 评估 RNOH（React Native OpenHarmony）把 RN 代码原生化 | RNOH 已进入 RN 官方支持矩阵但生态成熟度一般，先壳后迁，避免阻塞上架窗口 |
| 微信小程序 | **Taro（React 语法）** | 只做三件事：任务进度查看、成片/分镜分享卡片、灵感速记（语音/文字记 idea，回桌面端同步消费）。Taro 复用 React 写法，且可顺带产出 H5 版本 |
| 不选 Flutter | — | Dart 与现有 TS 资产无法互复用；`shared/` 与全团队 React 经验是最大存量资产，弃之可惜 |

小程序与 App 的数据通道均只连云端 SaaS；**移动端不提供本地部署模式**（手机跑不了 NestJS+PG，不做伪需求）。

### 4.1 移动端功能矩阵（明确"做什么、不做什么"）

| 功能 | iOS/Android (RN) | 鸿蒙壳 | 小程序 | 说明 |
|---|---|---|---|---|
| 项目列表 / 状态浏览 | ✓ | ✓(H5) | ✓ | 只读 |
| 任务进度 / 推送提醒 | ✓ | ✓ | ✓ | 轮询 + 厂商推送（P2 晚期接推送） |
| 一键创作（极速模式） | ✓ | ✓ | ✗ | 手机上只开最简输入；剧本/专业导演模式不给 |
| 分镜/资产图片浏览 | ✓ | ✓ | 分享卡片内 | 时间线/导演台/画布明确不做 |
| 灵感速记 | ✓（可离线记，回连后同步） | ✗ | ✓（文字/语音转文字） | 呼应 dashboard 的"最近项目"消费入口 |
| 成片播放 / 分享 | ✓ | ✓ | ✓（分享卡片 + 视频号合规审核注意） | 增长裂变入口 |
| API 通道配置 | ✗ | ✗ | ✗ | Key 配置只留桌面/网页端 |

不做的理由：`client/src` 的画布类页面（`CanvasStudioV2`、`FreeCanvas3`）依赖 `@xyflow/react` 鼠标级交互与毫米级缩放，移动复刻的性价比远低于"桌面创作 + 移动盯盘/分享"闭环。

## 五、"本地部署 ↔ 连接云端"切换机制设计

### 5.1 连接配置 UI（设置页新增"部署形态"区块，扩展 `client/src/pages/Settings`）

```
┌─ 部署形态 ────────────────────────────────────────┐
│  ◉ 纯本地（数据不出本机）      ○ 连接云端（多设备）   │
│  云端服务器地址: [ https://cloud.yimu.com    ]      │
│  访问令牌:       [ eyJhbGciOi...        ] [测试连接] │
│  连接状态: ● 已连接 · 账号 zhang@x.com · 剩余额度 86 │
│  [ 把本地项目迁移到云端… ]  [ 从云端拉取到本地… ]     │
└───────────────────────────────────────────────────┘
```

- 配置持久化在本地 `localStorage` + 壳层配置文件（Tauri store 插件），**切换形态需重启内嵌后端或重载 WebView**。
- 客户端 API 层收敛为单出口 `apiBase()`：本地模式指向 `http://127.0.0.1:<port>`，云端模式指向配置的 URL；请求头差异由出口统一注入（本地模式注入 `x-yimu-user-id`——`scripts/gateway.js` L161 已预留该分支，云端模式带 `Authorization: Bearer`）。

### 5.2 数据迁移

- **本地 → 云端**：后台提供 `POST /api/migration/export`（项目 JSON 全量包 + 资产清单；分镜/圣经/智能体消息均在现有 11+ 张表内，见 `docs/功能列表.md` §数据库表）与逐资产上传。云端按"导入新项目"入账，**不做在线双向同步**（避免冲突解决的无底洞）。
- **云端 → 本地**：同接口反向，下载项目包 + 资产落到本地磁盘 driver。
- 迁移 UI 明确提示：迁移是**复制不是搬移**，两边独立演化。

### 5.3 离线优先策略

- 桌面本地模式：天然全离线（内嵌后端 + 本地 PG + 本地存储），仅"生成"动作需要外网调模型 API（沿用 `server/modules/providers/` 的用户自带 Key 三通道）。
- 桌面云端模式：**读缓存 + 写排队**。React Query 已是全局数据层（`package.json`），开启 `persistQueryClient` 持久化查询缓存；创建/编辑类操作进本地队列，恢复联网后按序重放，冲突以"服务器版本更新时间戳"提示手工取舍。
- 小程序/移动端：不做离线写，仅缓存最近浏览（分镜图缩略图本地缓存）。

## 六、统一后台改造清单（一套代码、两种部署）

改造原则：**核心域零分叉**（`server/app.module.ts` 中 19 个模块不动业务逻辑），只在"接入层/适配层"做条件实现。

| # | 改造项 | 内容 | 涉及现状 |

### 6.1 鉴权 API 端点明细（新增 `server/modules/auth/`）

```
POST /api/auth/register          # 邮箱+密码（云形态开启；本地形态此路由 404）
POST /api/auth/login             # → { accessToken, refreshToken, tenant }
POST /api/auth/refresh           # 刷新令牌轮换
GET  /api/auth/me                # 当前用户 + 租户套餐/剩余额度（工作台顶栏展示）
POST /api/auth/logout            # refresh 令牌入黑名单（Redis，本地形态进程内）
```

关键实现约束：

1. `TenantGuard` 挂 `APP_GUARD` 全局注册（参照现有 `APP_FILTER`/`APP_INTERCEPTOR` 写法，`server/app.module.ts` L55-66），`@Public()` 装饰器豁免健康检查与登录端点；
2. **本地形态直通逻辑放在 Guard 内**（`DEPLOY_MODE=local` → 注入 `{ tenant: 'local', user: 'local-user' }`），与 `scripts/gateway.js` L50 的 `local-user` 身份保持同源，避免历史数据归属漂移；
3. 管理接口沿用现有 `x-admin-token` 机制不动（`docs/企业版部署.md` §三），两套凭据各管各的。

## 九、一句话总结

**统一后台已经存在（`server/app.module.ts` 的 19 个模块），缺的是商业三层（鉴权/租户/收单）和本地内嵌（PG/ffmpeg/Node sidecar）。** 客户端壳选 Tauri 2、spike 失败备选 Electron；本地数据库内嵌 PG 零改造、SQLite 缓行；移动端轻量做、只连云。所有形态差异收在 `DEPLOY_MODE` 适配层，核心域一套代码不分叉。
