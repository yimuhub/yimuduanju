## 二、自身的程序开发员维度深度评测

### 2.1 架构演进与双网关分裂隐患

从后端模块装配（[server/app.module.ts](file:///Users/czmj/Documents/yimuduanju/server/app.module.ts)）来看，工程共划分了 19 个业务模块，涵盖项目管理、制作圣经、分镜、资产、生成队列、模型供应商、质检、模板、看板、智能体、自由画布代理、导出、计费、管理后台、存储、剧本技能与向量记忆。这种模块边界在初期保证了极高的功能迭代速度，但在演进过程中形成了两套互不统属的模型调用与状态持久化体系。

第一套是以 [model-gateway.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/generation/model-gateway.service.ts) 与 [job-worker.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/generation/job-worker.service.ts) 为核心的标准异步生产管线。该管线支持通过 [routing.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/generation/routing.service.ts) 进行预算档位路由，支持通过 `StageBindingsService` 进行分环节模型绑定，受 [budget-cap.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/generation/budget-cap.service.ts) 月度预算上限守卫约束，并将任务状态、Token 用量与结算成本写入 PostgreSQL 的 `generation_jobs` 与 `projects.total_cost` 表字段。

第二套则是为支撑「自由画布」而独立编写的 [pavo3.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/pavo3/pavo3.service.ts)。代码对比表明，`Pavo3Service` 完全绕过了 `ModelGatewayService`、`RoutingService`、`BudgetCapService` 与 `BillingService`，直接查询 `model_providers` 表并在 HTTP 请求生命周期内同步发起 `fetch` 调用。这种双轨分裂引发了三重严重工程后果：其一，通过 `/api/pavo3/generate` 发起的所有文本、图片、视频、音频生成均不产生 `generation_jobs` 记录，不触发月度预算熔断，也不计入项目真实账单；其二，协议适配逻辑不一致，`ModelGatewayService.generateVideo` 针对火山方舟使用 `${baseUrl}/contents/generations/tasks`，针对 Agnes 使用 `/videos` 与 `/agnesapi`，针对 OpenAI 兼容接口使用 `/video/generations`（单数），而 `Pavo3Service.generateVideo` 硬编码调用 `${baseUrl}/videos/generations`（复数），导致在设置页配置火山方舟或 Agnes 通道时，自由画布 的视频生成必然报错 404；其三，`Pavo3Service.generateVideo` 在控制器请求内执行最多 20 次×2 秒（共 40 秒）的同步阻塞轮询，一旦视频生成耗时超过 40 秒（主流视频大模型通常需 60 至 180 秒），接口即返回 `{ ok: false, message: '视频任务排队中（已等待 40s），请稍后重试继续等待' }` 且丢弃远端 `taskId`，前端重试将重新发起 POST 请求并造成重复扣费。

### 2.2 并发安全、数据库存储与硬编码缺陷

深入审查后端核心服务源码，可以定位到多处影响生产稳定性的代码级缺陷。在 [model-gateway.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/generation/model-gateway.service.ts) 第 108 行，单例服务定义了实例属性 `private lastTextUsage: { model: string; inputTokens: number; outputTokens: number } | null = null;`，并在 `generateText()` 完成后由 [job-worker.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/generation/job-worker.service.ts) 第 410 行调用 `takeLastTextUsage()` 读取。由于 `JobWorkerService` 在 BullMQ 模式下默认开启并发消费（`JOB_WORKER_CONCURRENCY` 默认为 2，最高可设为 8），多个并发文本生成任务会同时读写同一个单例上的 `lastTextUsage` 字段，导致任务 A 的 Token 用量被任务 B 覆盖或窃取。

在多媒体数据存储层，[model-gateway.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/generation/model-gateway.service.ts) 的 `generateImage` 默认请求 `response_format: 'b64_json'`，而 `generateTTS` 与 [pavo3.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/pavo3/pavo3.service.ts) 的 `generateAudio` 均将二进制 WAV 音频流直接转换为 `data:audio/wav;base64,...` 字符串。虽然 `JobWorkerService.processImage` 通过 `ensureLocalUrl` 将图片落盘至 `/uploads/`，但 `processTts`（[job-worker.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/generation/job-worker.service.ts) 第 490–496 行）仍直接将数兆字节的 Base64 音频字符串写入 `shots.voice_url` 列，且 `processImage` 仍将包含完整 `b64_json` 的 `images` 数组原样写入 `generation_jobs.output_data` JSONB 列。这不仅会导致 PostgreSQL TOAST 表急速膨胀和查询内存激增，还导致本地相对路径 `/uploads/...` 或 `data:` URI 在后续传给远端视频生成接口时因不满足公网 `^https?:\/\//i` 校验而被静默丢弃。

在跨平台与环境可移植性方面，[export.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/export/export.service.ts) 第 456–458 行存在严重的开发者本机路径硬编码：
`const ffmpegBin = process.env.FFMPEG_PATH || (process.platform === 'darwin' ? '/Users/shanziya/.local/bin/ffmpeg' : 'ffmpeg');`
这意味着在任何未显式设置 `FFMPEG_PATH` 环境变量的 macOS 设备（如当前生产或客户 Mac 环境）上，只要不存在 `/Users/shanziya/.local/bin/ffmpeg` 目录，即便系统 PATH 中已通过 Homebrew 安装了标准 `ffmpeg`，服务端成片合成接口 `assembleFinalVideo` 也会直接因 `spawn ENOENT` 崩溃并抛出合成失败异常。同理，[docs/操作说明书.md](file:///Users/czmj/Documents/yimuduanju/docs/操作说明书.md) 中多处硬编码了 `cd /Users/shanziya/Documents/yimuduanju`。

此外，[server/modules/memory/memory.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/memory/memory.service.ts) 第 20 行导出的 `MemoryService` 类遗漏了 `@Injectable()` 装饰器（尽管构造函数参数带有 `@Inject(DRIZZLE_DATABASE)`），且默认加载的 `Xenova/all-MiniLM-L6-v2` 为英文语料训练的句向量模型，对中文剧本与人物小传的语义表征能力极弱，加之向量以 `doublePrecision[]` 数组存于普通表并在 Node.js 内存中拉取 200 行循环计算余弦相似度，缺乏 `pgvector` 索引支撑。

### 2.3 安全边界、依赖治理与工程化测试

在安全加固方面，工程通过 [crypto.util.ts](file:///Users/czmj/Documents/yimuduanju/server/common/crypto.util.ts) 实现了 `enc:v1:` 前缀的 AES-256-GCM API Key 落库加密，并在 [scripts/gateway.js](file:///Users/czmj/Documents/yimuduanju/scripts/gateway.js) 中默认绑定 `127.0.0.1` 且收敛了 `x-admin-token` 的注入范围。然而，安全审计仍发现三处高危风险：
1. **服务端请求伪造（SSRF）与任意文件探测风险**：在 [export.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/export/export.service.ts) 的 `downloadClip` 与 `curlOnce` 方法中，后端直接将数据库 `shots.video_url` 作为参数传给 `/usr/bin/curl -sS -f -L` 及 `fetch`。由于分镜更新接口允许修改镜头属性，若未对 `videoUrl` 的协议（必须限制为 `http:` / `https:`）与目标解析 IP（必须屏蔽 `127.0.0.0/8`、`10.0.0.0/8`、`169.254.169.254` 等内网及云元数据地址）进行白名单校验，攻击者可利用该接口探测内网服务或读取本地敏感文件。
2. **网关身份头无条件信任**：[scripts/gateway.js](file:///Users/czmj/Documents/yimuduanju/scripts/gateway.js) 对所有非静态请求自动注入固定 `x-larkgw-suda-webuser`（`user_id: 'local-user'`），且若在 Docker 或企业局域网环境中将 `GATEWAY_HOST` 设为 `0.0.0.0`，由于网关自身会自动从环境变量读取 `ENTERPRISE_ADMIN_TOKEN` 并为所有发往 `/api/admin/*` 及 `/api/billing/official` 的请求自动注入 `x-admin-token`（见 [scripts/gateway.js](file:///Users/czmj/Documents/yimuduanju/scripts/gateway.js) 第 128–136 行），任何能访问网关 5173 端口的客户端都等同于自动获得了最高管理员权限！这是一个极其隐蔽的权限提升漏洞：网关代填了 `x-admin-token`，导致后端的 `AdminGuard` 形同虚设。
3. **依赖分类错位与构建体积膨胀**：在 [package.json](file:///Users/czmj/Documents/yimuduanju/package.json) 中，`react`、`react-dom`、`react-router-dom`、`zustand`、`@reduxjs/toolkit`、`three`、`echarts`、`recharts`、`gsap`、`framer-motion`、`@tiptap/*`、`slate`、`slate-react` 等全部前端核心运行时库被错误地放置在 `devDependencies` 中，而 `dependencies` 混入了 `@ffmpeg/ffmpeg` 与 `@huggingface/transformers`。同时，项目中并存了 Zustand 与 Redux Toolkit 两套状态管理、Tiptap 与 Slate 两套富文本编辑器、ECharts 与 Recharts 两套图表库，以及 `CanvasStudio`（旧版残留）、`CanvasStudioV2` 与 `FreeCanvas3` 三代画布代码。

## 三、自身的产品经理维度深度评测

### 3.1 产品定位与核心价值闭环审视

从产品战略视角来看，[一幕·YIMU AI 短剧创作平台](https://github.com/yimuhub/yimuduanju)切中了当下 AIGC 影视与短剧漫剧赛道最核心的痛点——即如何将碎片化的文生文、文生图、图生视频、TTS 配音工具串联为一条「工业化流水线」。产品设计文档（[AGENTS.md](file:///Users/czmj/Documents/yimuduanju/AGENTS.md)、[docs/功能列表.md](file:///Users/czmj/Documents/yimuduanju/docs/功能列表.md)）清晰地定义了「一句话创意 → 剧本 → 制作圣经（世界观/角色/场景）→ 分镜表 → 关键帧/白模 → 视频生成 → 配音 → 质检 → 导出」的 12 步状态机闭环，并创新性地引入了「短剧（前 3 秒钩子检测）」与「广告（尾镜 CTA 检测）」双内容模式（[qc.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/qc/qc.service.ts) 第 264–290 行），在同类开源/源码可见产品中展现出极强的垂直行业认知。

然而，当前产品的最大结构性矛盾在于**「标杆产品全量复刻」导致的主线工作流割裂**。在项目工作台（[ProjectWorkspacePage.tsx](file:///Users/czmj/Documents/yimuduanju/client/src/pages/ProjectWorkspace/ProjectWorkspacePage.tsx)）中，同时存在三个全屏画布入口：「无限画布」（对应 `CanvasStudioV2/PavoCanvas.tsx`）、「一键成片」（路由 `canvas-auto`，当前实际渲染的仍是同一个 `PavoCanvas` 组件，并未真正拆分为独立流水线）以及「自由画布」（对应 `FreeCanvas3/FreeCanvas3Page.tsx`）。更重要的是，这三套画布的数据均存储在浏览器的 `localStorage` 中（键名分别为 `yimu-pavo-v1-{projectId}-ep{episode}` 与 `yimu-free3-{projectId}`），与项目工作台其余 13 个标签页所连接的 PostgreSQL 数据库表（`scenes`、`shots`、`characters`、`locations`、`assets`）处于**完全隔离的数据孤岛状态**！用户在「剧本」「人物」「分镜」标签页精心生成的角色和分镜，进入「自由画布」后一片空白；反之，在「自由画布」或「无限画布 v5」中生成的角色四视图、3D 导演台站位图和视频节点，也不会同步回写到项目的分镜表、时间线和导出页。

### 3.2 AI 短剧第一性原理：角色一致性与成片合成断层

对于 AI 短剧与漫剧而言，决定产品生死存亡的两个核心指标是**「跨镜头角色与场景一致性」**和**「最终成片的音画字一体化交付」**。代码审计表明，这两大核心环节目前仍停留在表层拼接阶段：
1. **角色一致性机制薄弱**：在分镜生成与图像生成链路中，虽然 `characters` 表设计了 `canonicalDescription`、`forbiddenChanges` 与 `referenceImageUrls` 字段（[server/database/schema.ts](file:///Users/czmj/Documents/yimuduanju/server/database/schema.ts) 第 415–438 行），但在 [model-gateway.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/generation/model-gateway.service.ts) 的 `generateImage` 接口中，请求体仅接收 `{ prompt, model, size, n, negativePrompt }`，**完全没有向图片生成 API 传递 `image` / `reference_images`（垫图/角色参考图）或固定 `seed`**！这意味着结构化工作台中的分镜首帧生成实际上退化为了纯文生图（Prompt 拼接角色外貌文字），无法利用即梦/Seedream、Midjourney Omni-Reference 或 Flux Redux/IP-Adapter 的视觉参考能力锁定角色脸部与服装；反而在独立的 `Pavo3Service.generateImage` 中传递了 `body.image = refImage`。
2. **成片合成「有画无声无字幕」**：在最终交付环节，后端 [export.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/export/export.service.ts) 的 `assembleFinalVideo`（第 430–528 行）仅从数据库筛选具有 `videoUrl` 的镜头，通过 `ffmpeg -f concat` 简单拼接视频流，且在重编码兜底分支中显式传入了 `-an`（静音参数）。该合成逻辑**完全忽略了镜头已生成的配音文件（`shots.voiceUrl`）、音效（`shots.sfxUrls`）、背景音乐（BGM）以及卡拉 OK 字幕（`getKaraokeAss`）**！用户走完「剧本→分镜→生图→生视频→生成配音→字幕」全套流程后，点击合成导出的 MP4 却是一段没有任何配音、BGM 和字幕的纯画面拼接视频，必须再手动下载剪映草稿并自己在本地把远端媒体 URL 下载替换后才能在剪映中合成。

### 4.1 高频专业创作流效率与亮点体验

### 4.2 重度生产力瓶颈与高频卡点

尽管单点工具亮眼，重度用户在长篇多集短剧（如 20–80 集连载漫剧）的高强度生产中会遭遇五大严重生产力瓶颈：
1. **画布数据存 `localStorage` 导致跨设备丢失与容量爆炸**：无论是 `CanvasStudioV2` 还是 `FreeCanvas3`，所有节点、连线乃至部分 Base64 缩略图/生成结果均保存在浏览器 `localStorage` 中。浏览器 `localStorage` 通常仅有 5MB 配额，一旦重度用户在画布中生成十余张 Base64 图片或开启多集创作，就会触发 `QuotaExceededError` 导致画布无法保存；且换一台电脑、清理浏览器缓存或团队多人协作时，画布工程瞬间清零。
2. **缺少「跨集资产库（Series Bible）」与多角色音色绑定**：目前 `characters`、`locations` 和 `memory_chunks` 均严格外键绑定在单个 `project_id` 下（[server/database/schema.ts](file:///Users/czmj/Documents/yimuduanju/server/database/schema.ts)）。短剧重度用户往往按「单集一个 Project」或「一部剧几十集」进行管理，当前架构无法在多个 Project 之间共享同一套主角团设定、固定音色（`voiceId`）和场景资产库。同时，在 `processTts`（[job-worker.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/generation/job-worker.service.ts) 第 471–502 行）中，TTS 生成完全没有读取当前镜头对白所属角色的 `characters.voiceId`，而是全片所有角色统一使用 Provider 默认音色（如 `alloy`），导致男女主角与反派在成片中用同一个声音说话！
3. **剪映草稿无法直接打开**：`getJianyingDraft` 导出的只是单文件 `draft_content.json`，其中的视频与音频 `path` 字段填写的仍是 `/uploads/...` 或云端 URL。剪映专业版仅识别本地绝对路径或草稿目录相对路径，且需要配套的 `draft_meta_info.json` 才能在剪映草稿箱中显示。重度用户拿到单个 JSON 文件后，仍需手工编写脚本下载全部视频/音频并批量替换路径，极大削弱了「一键导出剪映」的实用价值。
4. **抽卡对比（Takes / Variants）与局部重绘工作流缺失**：虽然数据库 `assets` 表预留了 `version` 与 `parentAssetId` 字段，且 `job-worker.service.ts` 提及了 `variantGroup`，但前端分镜表与导演台缺乏直观的「一镜多抽（Take Carousel）」「历史版本回滚」「首尾帧顺接（一键将镜头 N 的尾帧设为镜头 N+1 的首帧）」以及图片局部重绘（Inpainting）交互。

### 5.1 零基础用户的认知负荷与首次体验断层

站在没有任何编程或专业影视后期背景的「小白用户」（自媒体新人、网文作者、个人副业创作者）视角，从拿到项目到产出第一支有声有画的 90 秒短剧，目前存在四道极易导致流失的门槛：

第一道门槛是**环境安装与「先配 API Key 才能用」的配置迷宫**。虽然项目提供了跨平台安装脚本（`install-macos.sh`、`install-windows.bat`）并在 [scripts/gateway.js](file:///Users/czmj/Documents/yimuduanju/scripts/gateway.js) 中修复了根路径 `/` 自动 302 跳转 `/app/yimu/` 的问题，但 README 与多处文档（[README.md](file:///Users/czmj/Documents/yimuduanju/README.md)、[docs/安装指南.md](file:///Users/czmj/Documents/yimuduanju/docs/安装指南.md)）仍反复警告「必须通过 `/app/yimu/` 前缀访问，否则白屏」，给新手造成强烈的心理畏惧。更关键的是，当小白用户进入「设置 → 模型服务」添加火山方舟或中转站时，需要同时理解并填写 `Base URL`、`API Key`、`文本模型（Endpoint ID）`、`图片模型`、`视频模型`、`TTS 模型`、`音色 ID` 与 `请求格式（volcengine_ark / openai / agnes）` 共 8 个高度技术化的字段。对于火山方舟而言，用户往往分不清模型名称（如 `doubao-seed-1.6`）与推理接入点 ID（`ep-2026xxxx`），极易因填错单个字段导致后续全链路生成失败。

第二道门槛是**「假完成」错觉与自动化断链**。小白用户在「一键创作」页（[CreateWizardPage.tsx](file:///Users/czmj/Documents/yimuduanju/client/src/pages/CreateWizard/CreateWizardPage.tsx)）选择「极速模式」，输入一句话创意并点击「开始生成」后，进度条显示「正在创建项目...」，随后在 `storyboard_ready` 或 `assets_generating` 状态（仅耗时数秒完成启发式剧本拆分并把首帧图片任务塞入队列）就**立即在 800ms 后自动跳转进入项目工作台**（见 `CreateWizardPage.tsx` 第 279–295 行）。此时小白用户以为「90 秒短剧已经生成完毕」，结果进入工作台一看：分镜里既没有视频也没有配音，甚至连图片都还在后台排队或因为未配好 TTS/视频模型而报错；而要把所有分镜图片转成视频、配好音并合成为 MP4，还需要在工作台十几个标签页之间手动来回切换点击。

第三道门槛是**16 个工作台导航项的严重认知过载**。项目工作台顶部虽然将 16 个页签分为了 6 组（`概览`、`剧本圣经`、`美术资产`、`镜头`、`画布`、`交付`），但小白用户完全无法理解：**「分镜」「导演台」「时间线」「无限画布」「一键成片」「自由画布」这 6 个看起来都能做镜头的入口究竟有什么区别？** 尤其是点击「无限画布」和「一键成片」会跳出完全一模一样的页面（`PavoCanvas`），而点击「自由画布」又跳出一套风格相似但数据完全不互通的 `FreeCanvas3Page`，极易让新手迷失方向。

## 六、自身的平台运营经理维度深度评测

### 6.1 商业化架构、计费风控与多租户能力评估

从平台运营经理（负责 SaaS 商业化变现、API 成本毛利管控、用户增长留存、模板生态与内容合规）的视角审视，该项目已经搭建了颇具前瞻性的商业化雏形，包括 [billing.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/billing/billing.service.ts) 中的三级价格档位表（`budget` / `balanced` / `flagship`）、市场参考价对比（下单前展示「本次预估 ¥X，对比市场省 ¥Y」）、官方直供影子通道（服务端托管 Key）以及企业版 License 签发与审计日志（[docs/企业版部署.md](file:///Users/czmj/Documents/yimuduanju/docs/企业版部署.md)）。

然而，若要将该系统从「单机/私有化演示工程」推向「公网多用户 SaaS 运营」或「规模化商业交付」，当前架构存在五大运营级短板：
1. **缺乏真正的多租户隔离与用户认证计费账户体系**：尽管数据库表包含平台遗留的 `_created_by`（`user_profile` 复合类型）字段，但在业务查询层（如 `ProjectsService`、`AssetsService`、`GenerationService`、`BillingService`），绝大多数 SQL 查询（如 `this.db.select().from(projects)` 或 `getMonthlySpend()`）**并未按 `userId` 或 `tenantId` 进行硬性租户隔离（Row-Level Security 或 Where 条件过滤）**！本地网关固定注入 `local-user`，企业版 SSO 仅为一个返回配置状态的桩接口（`/api/admin/sso`），平台没有用户注册/登录、没有个人积分/余额钱包（`FreeCanvas3` 右上角的「200 积分」仅保存在前端 `localStorage` 中，用户刷新或修改浏览器存储即可无限重置积分！）、也没有充值支付（微信/支付宝/Stripe）与流水账本对账机制。
2. **计费与预算守卫存在重大漏损（Revenue Leakage）**：如开发维度所述，用户在「自由画布」中调用 `/api/pavo3/generate` 消耗的是后台配置的真实默认 Provider API Key，却完全不经过 `BillingService` 扣费，也不受 `MONTHLY_BUDGET_CAP_CNY` 预算上限拦截。此外，对于正常走 `JobWorkerService` 的任务，结算单价仅按任务次数（`unit: 'call'`）固定计费，未根据视频生成时长（4s vs 10s）或分辨率（720P vs 4K）进行阶梯成本核算，极易出现「用户生成 10 秒 4K 视频，平台按固定 2 元收费但上游 API 扣费 6 元」的毛利倒挂。
3. **缺乏运营数据埋点与转化漏斗分析**：目前 `DashboardModule` 仅统计数据库中的项目总数、镜头总数、任务状态分布与总费用，缺乏核心业务漏斗指标（如：一句话输入 → 剧本确认率 → 首帧生成率 → 视频转化率 → 导出完成率）、模型通道成功率/平均耗时 P95 监控面板以及报错归因统计（如多少失败源于上游 429 限流、多少源于敏感词拦截、多少源于余额不足）。
4. **模板生态与增长裂变机制缺失**：`TemplatesModule` 虽然支持「将项目存为模板」和按使用量排序，但模板分类与时长筛选仍停留在前端内存过滤，缺少「爆款短剧拆解模板库」「一键 Remix 同款」「带品牌水印的成片分享页」等低成本获客裂变抓手。
5. **AIGC 内容安全与合规风险**：作为短剧与视频生成平台，当前在剧本输入、提示词扩写、人物参考图上传以及视频导出全链路中，未接入任何文本/图像敏感词与违规内容审核（Content Moderation）机制，也未按照监管要求在导出视频或元数据中自动嵌入显式/隐式 AIGC 合成标识。

### 7.1 面向程序开发员的具体改造清单

1. **统一模型网关与消除并发竞态**：立即重构 [server/modules/pavo3/pavo3.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/pavo3/pavo3.service.ts)，将其内部的 `generateText`、`generateImage`、`generateVideo`、`generateAudio` 改为调用 `ModelGatewayService` 与 `GenerationService`，所有异步视频任务返回 `jobId` 由前端轮询 `/api/generation/jobs/:id`，彻底解决 40s 断连重发与计费逃逸问题。同时在 [model-gateway.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/generation/model-gateway.service.ts) 中删除实例属性 `lastTextUsage`，改为返回 `{ text, usage }` 结构。
2. **修复硬编码路径、音频 Base64 落库与 SSRF**：在 [export.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/export/export.service.ts) 中将 `ffmpegBin` 默认值改为 `'ffmpeg'`（并在启动时探测 `/opt/homebrew/bin/ffmpeg` 与 `/usr/local/bin/ffmpeg`）；在 [job-worker.service.ts](file:///Users/czmj/Documents/yimuduanju/server/modules/generation/job-worker.service.ts) 的 `processTts` 中调用 `ensureLocalUrl` 将 `data:audio/wav;base64,...` 落盘为 `/uploads/{projectId}/tts_{uuid}.wav`；在 `StorageModule` 中实现 S3/OSS/火山 TOS 适配器并生成公网预签名 URL，确保图生视频与首尾帧参考图能被云端大模型正常拉取。
3. **清理 `package.json` 依赖与冗余代码**：将前端运行时依赖迁回 `dependencies`，移除未使用的重复富文本与图表库，清理 `CanvasStudio` 旧版废弃目录，并补充针对 `ModelGatewayService`、`BillingService`、`ExportService` 的 Jest 集成测试与 Playwright 端到端冒烟测试。

### 7.2 面向产品经理、重度用户与小白用户的体验重塑建议

1. **收敛工作台导航与打通画布数据流**：将项目工作台的 16 个平铺页签精简整合为 **「故事与设定（剧本+圣经+角色+场景）」「分镜与制作（分镜表+导演台+无限画布视图切换）」「后期与合成（多轨时间线+质检+导出）」「任务与助手（侧边抽屉常驻）」** 四大核心阶段视图。废除画布 `localStorage` 独立存储，使画布上的每一个角色、场景、分镜节点直接对应 PostgreSQL 中的真实记录，实现「在分镜表改一句台词，画布节点实时同步；在 3D 导演台截一张站位图，直接绑定为对应镜头的 `startFrameUrl` 或白模参考」。
2. **补齐「多角色音色绑定」与「全量音画字 FFmpeg 合成」**：在剧本解析与分镜物化阶段（`processParseScript` 与 `processBoardsJob`），将每条对白自动关联到 `characters.id`；执行 `processTts` 时优先读取对应角色的 `voiceId`。在 `ExportService.assembleFinalVideo` 中，使用 FFmpeg `filter_complex` 将每个镜头的 `videoUrl` 与 `voiceUrl` 对齐混音（若人声长于画面则自动延长尾帧或提示调速），叠加背景音乐轨（人声出现时自动压低 BGM 音量），并通过 `-vf "ass=karaoke.ass"` 将卡拉 OK 字幕烧录进最终 MP4。
3. **重塑小白用户「零配置首作体验（First-Time User Experience）」**：在「设置 → 模型服务」中提供火山方舟、DeepSeek、OpenAI、硅基流动等主流厂商的**一键预设模板**（自动填好 Base URL、请求格式与推荐模型名，用户只需粘贴 1 个 API Key 并点击「一键自动探测可用模型」）。在「一键创作」页增加显式的模式选择：**「全自动成片模式（生成剧本后自动连跑分镜图、视频、配音与合成）」**与**「导演分步精修模式（每步暂停供人工确认）」**，彻底消除新手进入工作台后面对半成品不知所措的困惑。

### 7.3 面向平台运营经理的商业化与增长体系建议

1. **夯实多租户账户与服务端积分账本**：将网关固定注入的 `local-user` 升级为标准 JWT 登录态，在 PostgreSQL 所有核心业务表上强制校验 `created_by` / `tenant_id`。在 `billing.schema.ts` 中新增 `tenant_wallets`（积分/余额账户）与 `credit_ledger`（预扣冻结、成功实扣、失败退回流水表），按「模型档位 × 视频时长 × 分辨率」实现精准动态扣费，并将 `FreeCanvas3` 右上角的本地假积分替换为服务端真实余额。
2. **搭建运营全链路监控看板与合规网关**：在管理后台新增「全站转化漏斗与通道健康度看板」，实时追踪各供应商 API 的成功率、平均耗时、Token/调用成本及用户从创建到导出的各环节流失率；在提示词提交与资产上传入口挂载轻量级敏感词过滤与内容安全审核钩子，并在导出成片及元数据中注入符合监管规范的 AIGC 标识与可选品牌角标，结合「一键生成同款短剧模板链接」构建自传播增长飞轮。
